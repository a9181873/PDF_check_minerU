# PDF/OCR MacBook Air 與 OCI 效能比較（更新：2026-07-05）

## 測試條件

- 相同 6 對商品 DM、12 份 PDF、每輪合計 60 個輸入頁面。
- CPU-only，影像文字召回與 PaddleOCR 實驗預設關閉。
- Mac 最終結果採 `pixel-v4`，每案例 cold／warm 各 5 次，合計各 30 runs／300 input pages。
- Mac 分別量測主機原生 Python 3.12.8，以及正式 Linux ARM64 Docker 映像（10 vCPU、7.65GB 可用 RAM、image digest `ae7a3a83…`）。
- OCI 與修改前資料仍是每案例各 1 次工程基準；OCI 尚未部署最佳化版本，不能視為同版正式五輪比較。
- MacBook Air：Apple M4 10 核、24GB RAM。OCI：Ampere A1 4 OCPU、24GB RAM。

## 判讀

- Mac 正式 cold 初步 P95 比修改前工程基線低約 74.4%，通過 15 秒門檻。
- 完整 cold P95 為 38.45 秒；因實際執行 144 DPI 初步階段後再做 200 DPI OCR 完整階段，比舊單階段基線多約 32.9%，但仍有充足 90 秒餘裕。
- 正式 Docker 映像的 cold 初步／完整 P95 比 macOS 原生慢約 36.6%／45.7%，所以部署與硬體決策採容器數據 10.13／56.04 秒，不採較漂亮的原生數字。
- Docker 8GB 配額全程無 OOM，量測到的容器程序樹峰值 RSS 751MB；此數字不含 Docker VM 與檔案快取總開銷，正式多人環境仍保留 12GB 以上配置餘裕。
- `pixel-v4` 修正小型數字區塊被 NCC 過度抑制的問題；鳳守愛 `24→28` 現在初步階段即有視覺候選，正式五輪的初步區域召回為 100%。
- Docker 完整結果每個變更頁最多 3 個候選，低於上限 5，沒有以候選爆量換召回。
- cold 峰值 RSS 約 1.28GB；CPU 峰值受 Tesseract 子程序建立／退出影響而異常偏高，不作採購依據。
- 六對樣本仍只代表既有案例回歸；目前真值不完整，不能宣稱母體 precision ≥85% 或具統計代表性的 OCR 準確率。

## 硬體與部署決策

- 1–3 人低併發可先使用 MacBook Air M4／24GB；正式 Docker 映像在目前 8GB 配額已通過 SLA，暫無因速度採購 GPU 的必要。
- OCI A1 可保留低量常駐與遠端備援，但必須部署 `pixel-v4` 與 CPU-only Torch 映像後重跑相同五輪，才能做同版效能結論。
- 正式 CPU 映像已由錯誤的 `torch +cu130` 改為 `torch 2.12.1+cpu`，無 NVIDIA／CUDA 套件，約 764MB；不得用舊 CUDA 映像部署 OCI CPU 主機。
- 只有必要 VLM 無法在 90 秒內完成，且能正確解決至少 30% 待判讀區域時，再評估 16GB VRAM NVIDIA GPU。
